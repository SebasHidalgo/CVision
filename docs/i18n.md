# Interface languages (i18n)

English and Spanish, with i18next 26.5 and react-i18next 17.1 (pinned: the
27/18 majors were days old when this was written). No locale in the URL.

## How a request gets its language

`getLocale()` (`lib/i18n/server.ts`, memoized per request with React's
`cache`) resolves, in order:

1. the signed-in user's saved choice, `User.locale` (one primary-key read
   per request, only when signed in; a failed read counts as "none");
2. the `locale` cookie (one year, httpOnly, set by the switcher);
3. `Accept-Language`: the highest-ranked `es*` or `en*` entry wins; nothing
   we have → English (`lib/i18n/resolve.ts`, pure and tested).

The switcher (`components/i18n/LocaleSwitcher.tsx`, in the header and on the
account page) calls `setLocaleAction`, which writes the cookie and, signed
in, `User.locale`, then reloads the page: every server component, Clerk and
the analyses render again in the new language. Signing in on another browser
picks up `User.locale` on the first request.

Every page is rendered per request (the language depends on the request).
The legal pages used to be static; they are dynamic now.

### Future `/es` routes

Compatible. Every server helper takes an explicit locale (`getT(ns,
locale)`, `formatDate(value, locale)`, `renderAnalysis(feedback, locale)`),
so an `app/[locale]/…` segment (or a proxy rewrite) can pass the URL's
locale instead of the resolved one, and `generateStaticParams` could make the
landing static again per language. What would change: `getLocale()` would
read the segment first, and the switcher would navigate instead of reloading.

## Server and client

- **Server components**: `const t = await getT("<ns>")`. One i18next
  instance per request and locale (`cache`), never a shared mutable
  singleton. Markup inside a sentence: `<RichText ns i18nKey components />`.
- **Client components**: `useTranslation("<ns>")`. The root layout's
  provider holds only `common` and `errors`; a screen whose client
  components need more wraps them in `<ClientMessages ns={[…]}>`, which
  sends just those namespaces as props. The JSON never enters a client
  bundle. Errors: `useErrorCopy()`; dates: `useResetDate()`; the locale:
  `useLocale()`.
- **Dates, numbers, money** go through `Intl` with `en-US` / `es-419`
  (`lib/format.ts`). `es-419` writes the decimal point ("2.5") and "USD 15".
- **Third parties**: Clerk gets `localization` (es-MX from
  `@clerk/localizations` 3.37.10 with its "usted" strings moved to "tú",
  `lib/clerkLocalization.ts`); Paddle.js gets `settings.locale` (its own UI
  only: the product names come from the catalog, which Paddle shows in
  English). The interview room's interface follows the interface language;
  the interviewer's spoken language does not change with it.

## Adding a string

1. Add the key to `locales/en/<ns>.json` (English is the source of truth;
   keys are type-checked from it, `types/i18next.d.ts`).
2. Add the same key to `locales/es/<ns>.json`. Plurals: `_one`/`_other` in
   English, `_one`/`_many`/`_other` in Spanish (`_many` = `_other`; i18next
   asks for it at a million). Use `{{brand}}` for the product name.
3. `npm test` holds you to it: `lib/i18n/i18n.test.ts` (both locales, no
   empty values, same interpolation variables, plural forms, no "usted"),
   `lib/i18n/hardcodedStrings.test.ts` (no user-facing literal in JSX,
   attributes, toasts or copy modules), `screens/Home/wording.test.ts`
   (the wording rule in both languages), `lib/brand.test.ts`.

## Adding a locale

Add it to `LOCALES`, `INTL_LOCALE` and `LOCALE_NAMES` in
`lib/i18n/config.ts`; copy `locales/en/` to `locales/<new>/` and translate;
import the files in `lib/i18n/resources.ts`; teach `localeFromAcceptLanguage`
nothing (it reads `LOCALES`); add the plural forms the language uses to the
test; add a Clerk localization; add `DOMAIN_GLOSSARY` and the language name to
`lib/ai/prompts/translation.prompt.ts`; add the sentence templates
(`locales/<new>/sentences.json`).

## Analyses and interview feedback in another language

The canonical content is English, as measured in M8. A result never changes
with the language:

- **Code-made sentences are data** (`lib/ai/sentences.ts`): the headline,
  the outcome sentences of the job-fit paragraph and the notes code writes
  (years, accepted alternatives, the Languages advice, key-term notes,
  related matches) are stored as `{ key, params }` (`overall.headline`,
  `jobFit.outcomes`, `requirement.noteSentences`) and rendered at display
  time from `locales/<locale>/sentences.json` (`lib/i18n/sentences.ts`,
  `lib/i18n/analysisView.ts`). Params are verbatim words, numbers or
  language names. The English rendering is byte-identical to what the
  pipeline stored before (29 M8-H analyses replayed). The interviewer, the
  feedback prompt and the eval read the English view.
- **Model prose is translated once and stored** (`ContentTranslation`, one
  row per item and language, cascade from the analysis or the interview
  feedback). Translated: the summary, priority fixes (title, action),
  section descriptions, strengths, weaknesses, ATS problems and fixes,
  action plan, highlights, improvements, suggestions, the job-fit prose,
  strategic recommendations, the model's own requirement notes; in interview
  feedback, gap notes, why an answer worked, category comments, strengths,
  areas to work on, the final assessment (`lib/ai/translatableProse.ts`).
  **Never translated**: CV quotes and evidence, posting lines (row titles,
  `sourceQuote`), key terms and their CV words, skill names, roles,
  companies, figures, ATS sections and encoding artifacts, the priority
  fixes' impact level (an enum the interface labels), and suggested bullets
  (they go into the user's CV, in the CV's language).
- **The call** (`lib/ai/translation.ts`): Gemini Flash-Lite at temperature 0
  and seed 7, structured output with exactly the ids sent (`s0`, `s1`, …),
  a glossary built from the interface's own labels (statuses, kinds,
  dimensions, interview outcomes and categories) plus domain terms, and the
  protected terms of the analysis (key terms, CV words and skills that read
  as names, the company, the job title). Prompt version
  `TRANSLATION_PROMPT_VERSION`; bumping it invalidates every stored row.
- **Guards per string** (`lib/ai/translationGuards.ts`): present, not empty,
  the same digit groups (so "2.5" may become "2,5"), every protected term
  present in the source present verbatim, every quoted span unchanged, a
  sane length ratio (0.6–2× from 40 characters, 0.4–3× below), and not
  left in English. A string that fails keeps its English original; the
  stored `guardStats` say which check failed where (never the text) and the
  page says "Some parts couldn't be translated".
- **When**: right after an analysis is saved, inside the request, when the
  interface is not English and at least 8 s of the route's budget remain;
  otherwise on the first view: the page shows "Translating…", calls
  `translateAnalysisAction` / `translateFeedbackAction` once and refreshes.
  The claim is the unique insert of a PENDING row: a second tab waits for
  it. A failed call shows the original with "Translation unavailable" and
  is retried on a view 10 minutes later; a claim older than 60 s is taken
  over. A request that never reached the server offers the original
  (`?original=1`) instead of looping.
- **Cost control**: no quota is consumed; `translation` is rate-limited to
  30 calls an hour per user (`lib/plans.ts`), only for items the caller owns.
- **Measure**: `npm run eval -- translate <labels> --to <label> [--twice ids]
  [--print ids]` replays stored analyses into the structured form (free) and
  translates them with the production call and guards, on the routed tier
  and under the spend caps; `--print` renders an analysis as a Spanish
  reader sees it.

### Measured (M9, 2026-11-10/11)

Final code and prompt (`t1`), 16 synthetic analyses replayed from M8-H and
the 7 interview-feedback fixtures (M8-G run), free key:

| | |
|---|---|
| calls completed | 23/23 (the free tier answers 503 now and then; the harness retries) |
| strings that passed every guard | 643/643 |
| protected terms kept verbatim | 241/241 |
| digit groups kept | 30/30 |
| stability (same input twice) | 3/3 byte-identical |
| cost at standard prices | analysis USD 0.0033 (2,719 tokens), interview feedback USD 0.0019 |
| latency (free tier) | median 6.3 s, p90 8.4 s, max 12.8 s |

The two real postings (the owner's CV against Encora and Microsoft, two
analyses each, M8-H answers) on Flex: 104/104 strings passed, protected
terms 56/56, reruns byte-identical (3 of 3 comparable pairs); one call
failed after three Flex 503s. On the paid **standard** tier, the one
production uses, five analyses took a median **3.4 s** (3.1–3.6 s) and USD
0.0033 each: that is what translating inside the upload request adds to a
~9 s analysis, so the first view of a Spanish analysis is already Spanish.
Phase spend: USD 0.029 on the eval ledger (Flex 0.012, standard 0.017).

What the measurement changed before that run: language names were
protected terms ("English" must become "inglés": 11 strings of one analysis
failed), the prompt listed protected terms that no string contained and the
model inserted one ("accessibility (WCAG 2.1)" where the source said
"accessibility", caught by the digits guard), and the prompt now asks for the
second person where the English has no subject and keeps "stack" and
"pipeline". Before the fixes 627/643 strings passed; the quote guard caught
the model translating the CV's own section titles quoted in single quotes.

Read in full (three synthetic, the two real): the register is "tú" and the
glossary holds, with these known rough edges. Code-made sentences carry the
posting's own terms verbatim, so an English posting yields Spanish sentences
with English nouns (an invented example: "Tu CV muestra Kafka, pero no
stream processing", "la oferta acepta eagerness to learn it"): by design,
since key terms are never translated. The model still slips into the third person
on a subjectless English line now and then ("Posee una licenciatura…"), may
translate an institution's name, and writes "sección de educación" where the
interface says "Formación".

English term is always the same Spanish term, in the interface, the

**Wording rule, in both languages**: CVision is a self-assessment and
practice tool for job seekers ("herramienta de autoevaluación y práctica").
Never "evaluación de candidatos", "selección de personal", "decisiones de
contratación", "coaching", "preparación de exámenes"; the voice is an AI
interviewer ("entrevistador de IA"), never a person.
