# Database

Postgres on Supabase, through Prisma. What the schema is, how it changes,
how the app connects, and what a rebuilt database needs beyond the
migrations. The setup steps are in the README; this is the reference.

## The schema is the migration history

`prisma/migrations` is the history, and the database is only ever changed
by applying a migration file. There is no `db push`.

- `npm run db:migrate -- --create-only --name <what_changed>` after editing
  `prisma/schema.prisma`: Prisma writes the SQL into a new folder under
  `prisma/migrations`. **Read that SQL before applying it**: a renamed
  column arrives as a drop and an add, and a required column on a non-empty
  table needs a default or a backfill you write by hand into the file.
- `npm run db:deploy` applies what is pending; `npm run db:status` shows the
  history against the database.
- Migrations run over `DIRECT_URL` (port 5432, session mode), never over
  the transaction pooler. `migrate dev` also creates a temporary shadow
  database there; the Supabase `postgres` role can (`createdb`). If a
  shadow database is ever left behind by a pooler session, drop it with
  `DROP DATABASE ... WITH (FORCE)`.
- When `migrate dev --create-only` refuses to run without an interactive
  terminal (it happens when a unique is added), generate the SQL with
  `prisma migrate diff --from-url "$DIRECT_URL" --to-schema-datamodel
  prisma/schema.prisma --script` into a `YYYYMMDDHHMMSS_name` folder and
  apply it with `db:deploy`. `migrate status` only compares the history;
  drift is read with `migrate diff` (empty means none).
- **Every new table gets `ALTER TABLE "<Table>" ENABLE ROW LEVEL SECURITY;`
  in its migration.** Prisma does not model row-level security, and a
  database rebuilt from the history would otherwise come back with it off.
  The app connects as the table owner and bypasses RLS; nothing else may
  reach the tables (no policies, Data API off). `npm run db:check-rls` fails
  when any table in `public` has it off.
- A migration that touches `_prisma_migrations` must say `IF EXISTS`:
  Prisma never creates that table in the shadow database.

The client is generated by the `postinstall` script (`prisma generate`),
so a clean `npm ci` is enough; Vercel runs it too, which matters there
because its dependency cache can otherwise hand a build a stale client.

On Windows, run `npm run db:migrate`, `npm run db:deploy`,
`npx prisma generate` and `npm install` with the dev server stopped: while it runs it holds
the Prisma query engine open, and regenerating the client fails with
`EPERM` when it tries to replace the engine file.

## What Prisma does not do: `prisma/sql/bootstrap.sql`

Prisma's schema creates tables, columns, enums, primary keys, unique
constraints, foreign keys with their `onDelete`, and the indexes declared
with `@@index` / `@@unique`; `db:deploy` also replays the SQL written by
hand inside migrations (the RLS lines, the backfills). What it does not
model or watch: RLS on a table added later, policies, grants and revokes,
default privileges, the storage bucket and its limits. Those live in
`prisma/sql/bootstrap.sql`, idempotent and commented section by section:

1. RLS on every table in `public`, by a loop (a future table cannot be
   forgotten), `_prisma_migrations` included.
2. `REVOKE` from `anon` and `authenticated` on every table, sequence and
   function in `public`, and `ALTER DEFAULT PRIVILEGES` so tables created
   later by `postgres` are revoked too. Safe because the app always
   connects as `postgres`, the owner; `service_role` is left alone.
3. Hand-written indexes and constraints: none today (every one comes from
   the schema). The inventory of hand-written SQL per migration is in the
   file's header.
4. The bucket (`files-bucket`, private, 10 MiB, `application/pdf`) by
   `INSERT ... ON CONFLICT DO UPDATE` on `storage.buckets`, skipped with a
   notice on a database without the `storage` schema. Policies on
   `storage.objects` belong to `supabase_storage_admin` and are not
   touched: an offending one is named with the dashboard path.
5. A read-only report (tables with RLS off, policies in `public` and on
   `storage.objects`, grants to `anon`/`authenticated`, the bucket) to
   paste into the SQL editor; everything should come back empty or as
   expected.

`npm run db:bootstrap` runs, in order: `prisma migrate deploy`, the SQL
file up to its `-- @@report` marker over `DIRECT_URL`, `db:check-rls`,
`storage:setup --check`, then prints the report itself and one summary.
Without `--url` it uses `DIRECT_URL` from `.env`; any other URL needs
`--yes-i-mean-this-database`. `--skip-storage` is for a plain Postgres.
Proved on 2026-10-23 on a temporary database (twice, identical reports)
and on the development project (no change on the second run).

## Connections

`DATABASE_URL` points at Supabase's transaction pooler (Supavisor, port
6543) and carries three parameters that Prisma reads:

| Parameter | Local | Vercel | Why |
|---|---|---|---|
| `pgbouncer=true` | yes | yes | the transaction pooler cannot hold prepared statements |
| `connection_limit` | 5 | 3 | Prisma's own pool, per Node process (see below) |
| `pool_timeout` | 20 | 15 | seconds a query waits for a pooled connection before failing with `P2024` |

Why the numbers differ. Locally one long-lived dev server serves every
page, the status polls of every open tab, the `after()` feedback generator
and the webhooks at once; with `connection_limit=1` (the value Supabase's
Prisma guide suggests for serverless) they all queued behind a single
connection, and a `user.deleted` delivery once waited the full 10 s for one
and failed with `P2024`, with Clerk's retry completing it. Nothing holds a
connection across external I/O (every `$transaction` in the app is
database-only), so the queue was pure concurrency, and five connections
for one process is nowhere near the pooler's limits. On Vercel a Fluid
Compute instance also handles several requests at once, but many instances
run in parallel and all of them draw on Supavisor's pool, so each gets
fewer. Both values are small against the pooler's capacity (200 client
connections on the smallest compute); raise them only with a measurement
in hand. The round trip to the pooler from far away costs hundreds of
milliseconds, which is why the pages batch their reads into waves and why
production's functions must sit in the database's region (`vercel.json`).

`DIRECT_URL` (port 5432) is for the Prisma CLI and the scripts only.

## Tables

| Table | What it holds |
|---|---|
| `User` | one row per Clerk account: the id, a manual comp (`compPlan`), timestamps. Everything else hangs from it with `onDelete: Cascade` |
| `ResumeAnalysis`, `ResumeFeedback` | the posting and the CV's key; the analysis and its guardrail stats |
| `Interview`, `InterviewFeedback` | a rehearsal: sessions issued, transcript, failure reason, what paid for it; the feedback report |
| `UsageEvent` | the usage ledger: analyses, interviews, trials, credit grants and revokes; refunds mark, never delete |
| `RateLimitCounter` | fixed hourly windows per user and action, pruned on the next hit |
| `BillingCustomer`, `Subscription`, `BillingEvent` | the provider's customer id, a mirror of each subscription, and every accepted event id (no payload; outlives the account) |
| `GuardStatDaily` | anonymous daily tallies of what the guardrails did; never deleted |

Access rules, from `CLAUDE.md`'s data-layer section: every module under
`lib/database/` is `server-only`, resolves the session inside
(`requireUserId`) except the no-session modules the webhooks use, puts
ownership in the `where`, and answers `null` for a row that is missing or
someone else's. The only raw SQL in the app is the rate limiter's single
upsert statement, parameterized.
